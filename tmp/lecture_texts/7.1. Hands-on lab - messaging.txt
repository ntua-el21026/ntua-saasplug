Introduction to Messaging
It is the process of sending and receiving data or
■
information between applications
It is widely used in software development for
■
building distributed applications
Allows applications to communicate with each other
■
in a decoupled and asynchronous way
Several advantages (tbd)
■

===== PAGE 5/28 =====
Advantages of Messaging
Async communication between applications: sender
■
and receiver do not need to be available at the same
time
Decoupling: Apps can be developed and deployed
■
independently of each other
Scalability: Allows messages to be distributed accros
■
multiple instances or nodes
Fault tolerance: Allows messages to be retried or
■
routed to backup applications in case of errors

===== PAGE 6/28 =====
Comparison of Messaging with Other
Communication Methods
HTTP & direct API calls are synchronous
■
communication methods while messaging is
asynchronous
HTTP & direct API calls are typically point-to-point
■
communication methods (tightly coupled) while
messaging allows for loose coupling between apps
Messaging offers advanced features i.e. guaranteed
■
delivery, message persistence, pub/sub models etc

Messaging systems Overview
RabbitMQ: open-source broker that implements
■
Advanced Messaging Queuing Protocol (AMQP)
- provides a wide range of features such as message
persistence, message routing, and message priority
Apache Kafka: distributed streaming platform which
■
allows processing large amounts of data in real-time
- provides features such as scalability, fault tolerance, and data
retention
ActiveMQ: open-source message broker that supports
■
multiple messaging protocols such as AMQP, MQTT,
and STOMP
- provides features such as message grouping, message
filtering, and message expiration

===== PAGE 10/28 =====
AMPQ Overview (1)
Advanced Message Queuing Protocol enables
■
conforming client apps to communicate with
conforming messaging middleware brokers
Messaging brokers receive messages from publisher
■
and route them to consumers

===== PAGE 11/28 =====
AMPQ Overview (2)
Since it is a network protocol the publishers,
■
consumers and broker can all reside on different
machines
A producer is a user application that sends messages
■
A queue is a buffer that stores messages
■
A consumer is a user application that receives
■
messages

===== PAGE 12/28 =====
AMPQ Key Concepts (1)
Connection: A connection is a TCP connection
■
between your app and the RabbitMQ broker. AMPQ
is an application-level protocol that uses TCP for
reliable delivery
Channel: Virtual connection inside a connection.
■
When publishing or consuming messages from a
queue – all done over a channel

===== PAGE 13/28 =====
AMPQ Key Concepts (2)
Routing Key: Routing key binding with the queue
■
are rules that allow the exchange to put messages
into the queue
Exchange: The exchange receives messages from
■
the producer and from the other side it pushes
them to queues
Binding: A binding is a “link” that you set up to bind
■
a queue to an exchange

===== PAGE 15/28 =====
RabbitMQ Message Flow
Producer publishes message to the
■
exchange
Exchange receives the message
■
and is now responsible for the
routing of the message
A binding has to be set up
■
between the queue and the
exchange
The messages stay in the queue
■
until they are handled by a
consumer
The consumer consumes and
■
handles the message

===== PAGE 16/28 =====
Exchange Types
Direct exchange
■
Fanout exchange
■
Topic exchange
■
Headers exchange
■
Each type of exchange has its own routing rules, which
■
can be used to customize how messages are sent to
queues. By using the appropriate exchange type and
routing rules, it is possible to create complex routing
topologies that can handle a wide variety of messaging
scenarios.

===== PAGE 17/28 =====
Direct Exchange
Delivers messages to queues based on a message routing
■
key
Routing key is a message attribute added to the message
■
header by the producer
Routing key is used by the exchange to decide how to route
■
the message to the appropriate queue(s)
Message is routed to the queue(s) with the binding key that
■
exactly matches the routing key of the message
Useful for distinguishing messages published to the same
■
exchange using a simple string identifier

===== PAGE 19/28 =====
Topic Exchange
Routes messages to queues based on wildcard matches between
■
routing key and routing pattern specified by the queue binding
Messages are routed to one or many queues based on matching
■
between message routing key and pattern
Routing key must be a list of words delimited by a period (.)
■
Routing patterns can contain an asterisk (*) to match a word in a
■
specific position of routing key and a pound symbol (#) to indicate a
match of zero or more words
Consumers indicate their interest in specific topics by setting up a
■
queue and binding it with a given routing pattern to the exchange
All messages with routing key that match the routing pattern are
■
routed to the queue and stay there until the consumer consumes the
message

Topic Exchange - Example
SCENARIO 1

■

■

agreements.#
Routing key that matches example:
■
agreements.eu.berlin, agreements.us

===== PAGE 21/28 =====
Fanout Exchange
Copies and routes a message to all queues that are bound
■
to it, regardless of routing keys or pattern matching
Ignores routing keys provided
■
Useful when the same message needs to be sent to one or
■
more queues
Suitable for scenarios where different consumers need to
■
process the same message in different ways

SCENARIO 1

Queue A: Queue A
■

■

The message will be broadcasted to every

===== PAGE 23/28 =====
Headers Exchange
Routes messages based on arguments containing headers and optional
■
values
Similar to topic exchanges, it routes messages based on specific header
■
values rather than routing keys
A message is considered a match if the value of its header equals the value
■
specified upon binding
The "x-match" property, added in the binding between exchange and
■
queue, specifies if all headers must match or just one
"x-match" can have two values: "any" (at least one header pair must match)
■
or "all" (all header pairs must match)
Headers can be constructed using a wider range of data types, including
■
integer and hash
The headers exchange type is useful for directing messages containing a
■
subset of known (unordered) criteria
