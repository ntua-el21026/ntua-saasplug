## Docker Compose requirements

Use Docker Compose v2 syntax. A top-level `version` key is not required.

The Compose file must:

1. build `frontend` from `apps/frontend`;
2. build every backend service from its own `services/<service-name>` folder;
3. run Nginx as `nginx-gateway`;
4. run RabbitMQ with the management plugin image, such as `rabbitmq:3-management`;
5. run one PostgreSQL container for every stateful service;
6. create named volumes for PostgreSQL data;
7. place all services on a single internal development network, for example `saasplug-network`;
8. expose only the gateway to the host by default, using host port `8080`;
9. optionally expose RabbitMQ management on `15672` for development visibility;
10. avoid exposing PostgreSQL containers to the host by default;
11. use safe placeholder environment values compatible with `.env.example`;
12. work without a committed `.env` file by using Compose defaults where practical;
13. include health checks for Nginx, RabbitMQ, PostgreSQL, frontend, and backend services;
14. use `depends_on` with health conditions where appropriate.

Use canonical internal ports consistently:

```text
frontend: 5173
backend FastAPI services: 8000
nginx-gateway: 80 inside the container, 8080 on the host
rabbitmq: 5672 and 15672
postgres: 5432 inside each DB container
```

## Nginx gateway requirements

Create an Nginx config under:

```text
deploy/nginx/default.conf
```

The gateway must:

1. listen on container port `80`;
2. expose a gateway health endpoint at `GET /health`;
3. proxy `/` to the `frontend` container;
4. proxy canonical API prefixes to backend service containers;
5. add standard reverse-proxy headers:
   - `Host`,
   - `X-Real-IP`,
   - `X-Forwarded-For`,
   - `X-Forwarded-Proto`;
6. avoid direct browser calls to internal service ports;
7. avoid exposing provider APIs directly.

Use these gateway route prefixes for the baseline:

| Gateway path prefix | Upstream service |
|---|---|
| `/api/auth/` | `auth-service:8000` |
| `/api/provider-registry/` | `provider-registry-service:8000` |
| `/api/catalog/` | `catalog-service:8000` |
| `/api/status/` | `status-service:8000` |
| `/api/reservations/` | `reservation-service:8000` |
| `/api/analytics/` | `analytics-service:8000` |
| `/api/billing/` | `billing-service:8000` |

Provider adapter services are internal integration services. For smoke testing only, you may expose health-only gateway prefixes such as:

| Gateway path prefix | Upstream service |
|---|---|
| `/api/internal/providers/red/` | `red-provider-service:8000` |
| `/api/internal/providers/green/` | `green-provider-service:8000` |
| `/api/internal/providers/blue/` | `blue-provider-service:8000` |

If you add these internal prefixes, document clearly that they are development health/debug routes only and must not become direct browser/provider business APIs.
